1. THE CORE DECISION — read this before writing any CSS
--------------------------------------------------------------------------------
Lenis.dev is a MARKETING SITE. Its motion is SCROLL-driven: you scroll, the hand
turns. Beautiful, and wrong for us.

We are not a marketing site. We are an agent that DOES things. So our motion must
be STATE-driven: the agent listens, thinks, verifies, refuses, sends — and the
screen reacts to THAT, not to the scrollbar.

    Scroll-driven  = "look how cool this site is"
    State-driven   = "look what this agent just did"   <- this wins the demo

Keep Lenis for feel (it's 3kb, one line, makes everything smoother). But the
signature moment is the AGENT STATE MACHINE, not a scroll sequence.

THE THESIS THAT MAKES ANIMATION LEGITIMATE ON AN ACCESSIBILITY APP:
  One event stream drives BOTH the voice and the visuals. Same state change
  fires the ElevenLabs line AND the animation, at the same moment.
    - blind users get the audio
    - LOW-VISION users (most of our users) get big, high-contrast motion cues
    - sighted judges get the show
  Say this sentence in the pitch. It turns "pretty animations" into an
  accessibility argument, which is the whole difference between a nice UI and a
  UI that wins a prize on THIS project.

NON-NEGOTIABLE: prefers-reduced-motion must kill or flatten everything. Vestibular
disorders are a disability. Failing that check on an accessibility app is the one
mistake a judge will actually punish us for.


2. THE HAND-MODEL EQUIVALENT — our signature object
--------------------------------------------------------------------------------
Lenis's hand is a 3D WebGL model (Three.js / R3F). NOT achievable in 10 hours on
top of voice + agent loop. Don't try.

Our equivalent, and honestly a better fit: THE VOICE ORB.
A single SVG/canvas object, centre of the screen, driven by REAL audio amplitude
from a Web Audio AnalyserNode. Five states, each visually distinct:

  idle       slow breathing pulse, dim
  listening  deforms live to the user's mic amplitude
  thinking   slow orbit / shimmer, no amplitude
  speaking   deforms to the ElevenLabs output amplitude
  REFUSING   hard stop, desaturate, red ring, sharp shake — then still

The refusing state is the one nobody else will have. It is the ANS story made
visible. Build it last but do not cut it.

[ ] orb component with 5 states
[ ] wired to real mic amplitude (AnalyserNode)
[ ] wired to real TTS output amplitude
[ ] every state also announced via aria-live
[ ] reduced-motion: states become colour/text changes, no movement

5. THE VIBE — lock these once, apply everywhere
--------------------------------------------------------------------------------
[ ] DARK, high contrast, one accent. Near-black bg, warm off-white text.
    Rationale: low-vision users need contrast; dark reads as serious tooling
    rather than a consumer app; and it matches GoDaddy's own deck aesthetic
    (teal on near-black) which quietly flatters the ANS judges.

[ ] COLOUR ROLES — semantic, not decorative
      bg        near-black          #0A0F0F-ish
      text      warm off-white
      accent    teal/cyan           verified, active, trusted
      danger    red                 refused, blocked, unverified
      muted     grey                pending, idle
    Two signal colours only. Verified vs refused IS the product.

[ ] TYPE — one family. Inter or Geist. Sizes: 14/16/20/32/56. Nothing else.
[ ] SPACING — 8px grid. No exceptions.
[ ] CONTRAST — 4.5:1 body, 3:1 large. Check every accent on every bg.
[ ] RADIUS — pick one (8px or 12px) and never vary it.
[ ] FOCUS RING — visible, 2px, accent colour, on EVERYTHING. Non-negotiable.

Lock these in a tokens file on the homepage. Every later page imports it and
adds nothing new.
